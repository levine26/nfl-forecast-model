# Editorial acceptance ledger: shadow-only Phase B groundwork

This module is **not connected to the production writer**. It provides the persistent game-scoped content ownership missing from the current ephemeral Groq/ChatGPT pipeline, without touching official forecasts, locks, output generation, production code paths, or the existing public site.

## API and authority

`EditorialShadowLedger(root)` holds an immutable SHA-256-addressed record under `games/<game_id>/revisions/<sha>.json` and an atomic `games/<game_id>/current.json` acceptance pointer. It serializes mutations with a file lock and compare-and-swap `expected_revision`. It does not accept a provider response without an independently supplied validation receipt attesting both article resolution and claim support. That receipt **must be generated by a separate verified-source/football-quality gate**; this module checks the supplied receipt fields but cannot independently prove source truth.

`accept(...)` rejects outdated or conflicting provider output and preserves older immutable versions. `mark_freshness(...)` records new factual concerns without deleting the accepted record. `rollback(...)` can restore any previously preserved immutable version, but marks it for review. `prepare_shadow_release(game_ids, canonical_sha256=...)` fails on missing/withheld current records and produces a shadow-only release descriptor referencing canonical numeric input hash. It writes neither a production Read nor any official number.

## Trust boundaries

* Live network verification, article title/URL/content checks, current-roster attribution, exact claim-support excerpts, complete content receipts, substantive tactical quality validation, seven-word phrase checks, paragraph 2, and full-slate release publishing remain **outside** this ledger.
* Production validators and canonical deterministic numerical rendering remain unchanged.
* The ledger is a **storage primitive**, not an autonomous fallback worker. No credentials, Groq quota, or ChatGPT API access are inferred.
* During an eventual migration, persist accepted versions in a durable repo/GitHub artifact store, not merely an Actions runner's temporary workspace. The current module's durability applies to its filesystem; durable cross-run storage needs a separate verified workflow.
* A production cutover requires separate PR, approved workflow ownership, real Week 5 verified-source receipts, canonical numeric parity, fault injection, staging, and rollback rehearsal. Two active production editors are prohibited.
